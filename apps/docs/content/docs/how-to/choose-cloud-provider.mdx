Zuse supports **Boat** (formerly Box), **E2B**, and **boxd**. Choose a machine in the new-chat composer's
**Run on** menu: **Cloud · Boat**, **Cloud · E2B**, or **Cloud · boxd**. The choice applies to that
new chat. Existing chats stay on their original provider, including after a pause
or restart. Changing providers does not move an existing workspace's files.

Boat is Zuse's default when both it and E2B are available. It is a good starting
point for general development and larger builds. Choose E2B or boxd when preserving
running processes across ordinary pauses matters more to your workflow.
Available choices depend on which providers your Zuse deployment has configured.

| | Boat | E2B | boxd |
| --- | --- | --- | --- |
| Machine choices in Zuse | Small, Standard, and Large | The configured E2B template size | Small, Standard, and Large |
| Pause and resume | Disk state is preserved; Zuse restarts its runtime and agents | Normal pauses preserve disk and memory state | Pauses hibernate the machine; memory, processes, and files return on resume |
| Tradeoff | A cold resume can take longer while services restart | Memory restoration can avoid that restart, but reconnects and runtime updates still take time | Choosing a size other than the template's adds one reboot when the chat starts |
| Best fit | General coding, builds, and choosing more CPU or memory | Workflows that benefit from keeping processes alive between pauses | Long-lived chats that pause often and want their processes back in milliseconds |

Boat preserves files and installed packages when stopped; manually launched
processes need restarting. See [Boat's lifecycle overview](https://boat.dev/).
E2B normally preserves both memory and files; filesystem-only recovery can still
require a cold boot. See [E2B persistence](https://docs.e2b.dev/sandbox/persistence).
boxd hibernates a paused machine to disk and wakes it with its memory intact; see
[Suspend, resume, and hibernate](https://docs.boxd.sh/guides/suspend-resume).
These are lifecycle differences, not a promise that one provider is always faster.
Resume time also depends on the image, services, region, and current capacity.
Zuse subscription and usage charges are shown in Cloud settings; provider retail
pricing is not the price of your Zuse subscription.

## Prepare each provider

In **Settings → Cloud → Cloud image**, select **Machine provider**, then build or
update that provider's image. Each image includes your connected repositories.
Build Boat and E2B separately if you want to switch between them for new chats.
Updating one does not replace the other's image or running workspaces.

Connect your coding agents once in **Cloud Authentication**. The same account
credentials work on both machine providers; you do not authenticate each agent
again for E2B. Repository connections, uploads, queued delivery, port forwarding,
local-device command approvals, and workspace APIs use the same Zuse workflows.
Available choices depend on which providers your Zuse deployment has configured.

## Choose through the API

Pass `providerId` when creating a workspace through `POST /v1/api/workspaces`:

```json
{
  "projectId": "your-project-id",
  "providerId": "box",
  "agent": "codex",
  "model": "your-model"
}
```

Use `"e2b"` for E2B or `"boxd"` for boxd. Authenticate with your Zuse API key and supply an
`Idempotency-Key` header. Omitting `providerId` uses the deployment default.
An unavailable provider returns an error rather than silently switching machines.
The chosen provider must have a ready account image containing that project.

Account-authenticated image management supports
`GET /v1/cloud/image?providerId=box` and
`POST /v1/cloud/image/build` with
`{"providerId":"box","mode":"update","idempotencyKey":"unique-build-key"}`.
Use `e2b` or `boxd` to inspect or build the other images. Omitting the provider preserves the
default-provider behavior. Image management uses your account session, not a
workspace API key.

## Sending while paused

Send normally. Your message and attachments wait in the composer queue while
Zuse resumes the workspace. The prompt moves into the conversation when the
runtime takes the command. Cancel is available while the mailbox still allows
cancellation. Delivery failures and required sign-in remain visible next to the
composer; the gray cloud icon in the sidebar only identifies a cloud chat.


## Usage and cost

Cloud settings show usage attributed to your workspaces and image builds. For
Boat, Zuse uses [Boat's reported usage and cost](https://docs.boat.dev/api/reference/sandboxes/get-sandbox-usage),
which already accounts for machine size and excludes stopped time. Running usage
is provisional and can include a short reservation for continued operation;
confirmed usage is reconciled after the machine stops.

Boat reports list-price compute cost, before provider plan discounts or credits.
Your Zuse allowance, overage markup, and spending cap still determine your Zuse
bill. E2B and boxd use their configured compute rates. Provider choice alone
does not change your subscription price.
