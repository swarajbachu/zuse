The model is only one part of a coding agent's environment. The checkout, dependencies, terminal, and access to services determine what the agent can actually do.

Zuse supports local work and optional cloud environments. Choosing between them is a workflow decision: where should this task's files and tools live?

## Start local when your environment is ready

Local work is a good fit when the repository already builds on your machine and the task needs your installed tools. A fresh Git worktree can isolate a change while keeping the workflow close to the project you know.

Before starting several tasks, make sure the repository's setup script prepares each checkout. A new worktree has its own working files; it may need dependencies or generated files before a test can run. Confirm setup completed before interpreting a failure as a code defect.

## Use an isolated cloud workspace for remote compute

A cloud workspace provides a separate environment for the task. It can be useful when you want the work to run away from your laptop or need a reproducible setup for a repository.

Cloud does not make dependencies disappear. Connect the repository, configure setup, and authorize the coding agent for that environment. Keep secrets scoped to what the task needs. An agent that works locally may require authentication again in a different environment.

Zuse Cloud remains in beta. The Cloud Workspace plan includes a compute allowance, with additional compute billed according to the plan. Model subscriptions and API usage are separate from infrastructure usage. See the [pricing page](/pricing) for the current plan details.

## Decide before the first prompt

Ask four questions:

1. Does the task need tools or services available only on my machine?
2. Does it need a fresh checkout, a fresh environment, or both?
3. Have the repository setup and agent authentication been configured there?
4. What evidence will show that the result works in its intended environment?

Then choose the workspace and verify its identity in the composer. That one decision makes later file changes, terminal output, and compute usage easier to understand.

Continue with [choosing a cloud provider](https://docs.zuse.sh/how-to/choose-cloud-provider) or [starting with local worktrees](https://docs.zuse.sh/how-to/local-parallel-worktrees).

## Make the first cloud task reproducible

For a first remote run, choose a small change with a known check. Record the repository, branch, setup command, and agent authentication method before starting. If setup fails, fix the environment before asking the agent to change application code. Otherwise, an infrastructure failure can become an unnecessary patch.

After the run, inspect the actual checkout and diff. A readable transcript does not prove that a paused runtime has recovered its files, and a queued message does not prove that an agent executed it. The [cloud recovery journal](/blog/cloud-agent-recovery-journal) explains those boundaries. Start with the [open source cloud agents guide](/blog/open-source-cloud-agents) for the complete evaluation workflow.
