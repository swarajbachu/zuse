## What the screenshot is installing

The screenshot shows the third onboarding step, **Agent access**, with the message **Installing agent tools 0.21.12…**. That is the external **Callstack `agent-device` CLI and its daemon**, rather than Xcode, an iOS SDK, or a complete desktop computer-use agent. In the inspected revision, T3 pins `agent-device` to **0.21.23** and Expo's `expo-device-hub` to **0.15.3**. The screenshot therefore captures an older tool pin; its 0.21.12 label should not become the version requirement for new Zuse work. [Version constants and package entrypoints](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/DeviceToolchain.ts#L30-L88).

There are three distinct layers:

| Layer | Purpose | Installation/activation |
| --- | --- | --- |
| Xcode + iOS Simulator runtime / Android SDK + emulator | Platform environment and app building | Installed separately by the developer; T3 checks availability and gives guidance. |
| `expo-device-hub` | Device discovery, boot, screen streaming, manual controls | Installed and started after explicit device-support setup. |
| `agent-device` | Semantic accessibility snapshots, app launch/install, taps, text and automation | Separate agent-access step; daemon startup and CLI preparation are lazy after access is enabled. |

T3's device documentation explicitly separates prerequisites from the helpers it manages. Opening the Device panel by itself does not download or launch anything. [User setup and prerequisites](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/docs/user/devices.md#L10-L39).

## Why the extra tools install only when needed

Device support and agent control are independently disabled by default. `enableDeviceSupport` authorizes the server to install/run helper processes; `enableAgentDeviceAccess` authorizes providers to drive devices. A user can have the manual viewer without granting agent access. These are server settings, not a renderer-only toggle. [Settings contract](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/packages/contracts/src/settings.ts#L1156-L1172).

The stated design reasons are: separate user consent for manual versus agent controls; persistent pinned installs avoid transient `npx` caches and registry dependence on every reboot; supervised helper processes isolate native CoreSimulator crashes from the environment server. The interpretation for Zuse is to preserve the same optional capability boundary and avoid loading device helpers into every session. [T3 internal rationale](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/docs/internals/devices.md#L8-L18).

The step is conditional on **using device support/allowing agent control**, not on an app or tool called `zuse` being requested. Nothing in this T3 implementation recognizes a `zuse` command as the trigger. If “only installed when zuse is needed” means when our app needs device functionality, the appropriate trigger is explicit capability enablement or first authorized device use. [Service readiness and enablement gates](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/DeviceService.ts#L258-L339).

## Installation lifecycle and failures

Local tools live in `<T3 baseDir>/tools/<package>/<pinned-version>`. Runtime daemon/session state lives separately in `<stateDir>/device/agent-device`. The install is a real `npm install --prefix <staging> --no-fund --no-audit package@version`, with a ten-minute timeout; if npm is missing, the local implementation can run npm 11 through pnpm. It verifies the entrypoint, writes `.install-complete`, and renames the completed staging directory into place. Entry existence alone is insufficient because npm may have extracted only part of a package when interrupted. An in-process semaphore serializes local installers. [Install paths, completion check and staged install](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/DeviceToolchain.ts#L90-L240).

Installing a pinned top-level package is not the same as pinning all transitive npm dependencies: the command installs the published package and resolves its dependency ranges at install time. Zuse should decide whether to preserve this model or ship a lockfile/artifact manifest for stronger reproducibility. This is an inference from the installation command and the published hub dependency ranges. [T3 install command](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/DeviceToolchain.ts#L154-L183), [published hub artifact](https://registry.npmjs.org/expo-device-hub/-/expo-device-hub-0.15.3.tgz).

The hub runs on loopback in a separate supervised child with readiness checks, restart backoff, a recorded PID/entrypoint/port, and ownership checks before cleaning an old process. Agent-device runs an HTTP daemon in its own state directory, without its default idle timeout; T3 disables its update notifier and stops it explicitly. `devices --json` triggers daemon startup, after which T3 reads the generated port/token record. [Hub process lifecycle](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/LocalDeviceHost.ts#L296-L486), [agent daemon lifecycle](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/LocalDeviceHost.ts#L486-L581).

Tool inventory reads completed installs without downloading or starting anything. Required versions install on the next use, and T3 explicitly documents that a host needs network access for a new pin and does not silently fall back to an older version. Updating only a UI client does not update a remote environment server's tool pins. Maintenance keeps the current, previous and active versions, and refuses pruning if it cannot safely inspect active processes. [Inventory implementation](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/DeviceToolchain.ts#L249-L307), [update policy](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/docs/user/devices.md#L110-L118), [maintenance behavior tests](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/deviceToolMaintenance.test.ts#L17-L98).

## What is in the external packages

The inspected published `expo-device-hub@0.15.3` archive includes vendored `serve-sim` and `serve-emu`, native simulator modules and helper binaries, streaming code and a dashboard. Its runtime dependencies include `node-datachannel`, a native dependency. A hub install is therefore more than one tiny JS entrypoint. This does not imply that T3 exposes the whole hub dashboard or uses every transport it ships. [Exact published package archive](https://registry.npmjs.org/expo-device-hub/-/expo-device-hub-0.15.3.tgz), [upstream repository](https://github.com/expo/expo-device-hub).

The published `agent-device@0.21.23` archive declares no runtime npm `dependencies` or `optionalDependencies`; its compiled JS is packaged alongside platform helpers. The hub does declare runtime dependencies, so its dependency installation can involve native artifacts. The published `agent-device@0.21.23` metadata requires **Node >=22.12**. T3's remote probe checks only major version >=22, so Zuse should check the package's actual engine constraint rather than copy that weaker probe verbatim. Published npm metadata showed unpacked package sizes of approximately 5.1 MB for agent-device and 23.7 MB for the hub, excluding dependencies and generated build/cache data. These are artifact observations, not total installed-size estimates. [Exact agent package metadata](https://registry.npmjs.org/agent-device/0.21.23), [exact hub metadata](https://registry.npmjs.org/expo-device-hub/0.15.3).

For iOS interactions, first use builds an XCTest runner and can take a couple of minutes; this is separate from npm installing agent-device. The Android snapshot helper is also provisioned on first use. On iOS Simulator, agent-device's published README distinguishes its local accessibility bridge for snapshots from XCTest for interactions. Do not present the npm progress state as proof that the first tap will be instantaneous. [T3 quick-start platform notes](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/mcp/toolkits/device/handlers.ts#L48-L67), [published agent archive](https://registry.npmjs.org/agent-device/-/agent-device-0.21.23.tgz).

## Agent access and computer use

T3 exposes four device MCP tools: `device_list`, `device_open`, `device_screenshot`, and `device_close`. They handle lifecycle, visibility and image results. Taps, text, app installation and semantic snapshots run through `agent-device`, intentionally avoiding an ever-growing duplicate wrapper of the CLI's command set. The snapshot loop is `open` → `snapshot -i` → `click @eN` / `fill @eN` → screenshot; accessibility refs are preferred to coordinates. [Tool surface](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/mcp/toolkits/device/tools.ts#L30-L109), [returned workflow](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/mcp/toolkits/device/handlers.ts#L29-L68).

`device_open` returns the exact absolute launcher executable plus `--platform` and device ID (`--udid` or `--serial`), host config path and a session name. Its launcher requires both `--config` and `--session`, strips ambient daemon/config variables, and runs the pinned Node entrypoint. Host config files contain the daemon endpoint and authentication token, are atomic and mode 0600; the session name is derived from thread + host + device, so opening a second host does not retarget earlier commands. [Open handler](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/mcp/toolkits/device/handlers.ts#L150-L213), [launcher](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/AgentDeviceShim.ts#L16-L74), [host/session identity](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/AgentDeviceTarget.ts#L16-L54).

Current source deserves priority over older internal prose: `docs/internals/devices.md` says provider startup installs/starts the CLI and injects PATH. At this commit, `ProviderSessionManager.ts` prepares the `device` capability from effective access settings, while `device_open` itself creates the absolute launcher and `DeviceService.agentCli` lazily ensures the package. Codebase searches found no current call from provider startup to `ensureAgentDeviceShim` or `agentReadinessIfSupported`. The old environment helper still exists in provider-core, but is not evidence that every startup initializes devices. [Credential preparation](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/orchestration-v2/ProviderSessionManager.ts#L479-L540), [lazy CLI resolution](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/DeviceService.ts#L1147-L1164).

Each device tool requires a thread-scoped `device` capability; an outside MCP client without a T3 thread cannot simply open that thread's viewer. Screenshots are constrained to sessions opened in the calling thread. Access is issued with provider credentials and refreshed when capability settings change; the user docs recommend restarting an existing agent after enabling access. [Thread capability enforcement](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/mcp/McpInvocationContext.ts#L108-L136), [screenshot thread scoping](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/mcp/toolkits/device/handlers.ts#L215-L253), [agent user guidance](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/docs/user/devices.md#L72-L81).

This is **mobile device interaction**, not arbitrary control of macOS desktop windows, Xcode's UI or the whole user's computer. The upstream agent-device product has a broader platform surface, but T3's integration exposes iOS Simulators and Android Emulators through its own device contracts/tools. Full macOS computer use would be a separate Zuse capability with different capture/control permissions. [T3 tools explicitly describing supported targets](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/mcp/toolkits/device/tools.ts#L37-L59), [upstream platform scope](https://github.com/callstack/agent-device).

Disabling agent access has two effects with different timing. `DeviceService.configure({ agentAccessEnabled: false })` immediately stops agent daemons on configured hosts, and `agentTarget` rechecks the live support/access settings before opening a device. Already-issued MCP capability records, however, are snapshots: token resolution does not reread settings, and `device_list`, `device_screenshot`, and `device_close` check that credential rather than a live agent-access setting. With manual support still enabled, an existing session may retain those non-driving MCP calls until credential preparation rotates/revokes it. Thus “off” should not be described as immediate complete removal of every old session tool. Zuse should define and test whether disabling access revokes existing credentials, rather than infer that from the toggle. [Immediate stop](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/DeviceService.ts#L527-L575), [live agent target gate](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/DeviceService.ts#L928-L941), [credential issuance/resolution](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/mcp/McpSessionRegistry.ts#L123-L192). This is a source-based inference; it was not exercised against a running T3 server.

## Security and server ownership

The environment server owns discovery, helpers, devices and routing. The raw hub stays on loopback because its vendor surfaces include shell execution or unauthenticated actions. T3 forwards only allowlisted stream/read/config routes and a small set of mutations, authenticates through the environment session, requires operate scope for input/tuning, and strips upstream credentials/tickets. A client-facing arbitrary shell-exec proxy is explicitly excluded. [Authenticated allowlist and streaming proxy](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/DeviceHubProxy.ts#L1-L190).

Settings changes use typed `device.action` RPCs that execute specific `simctl`, `adb`, or vendored helper operations on the resolved host, then read back the state. This preserves a narrow boundary and makes the UI reflect actual device values. [Design boundary](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/docs/internals/devices.md#L37-L50), [typed action implementation](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/DeviceActions.ts#L141-L281).

## Remote Macs and cloud development

A Linux cloud server cannot run iOS Simulator itself. A configured SSH Mac host is the relevant route: SSH configuration/keys belong to the environment server; interactive passwords are unsupported. A connection test probes SSH, Node, npm and platform tools without installation. The first authorized listing starts pinned tools on the host. Remote script paths are `~/.t3/device/tools/<package>@<version>`, with per-owner runtime state in `~/.t3/device/hosts/<owner>`. Remote installs and lifecycle operations use filesystem ownership locks. [Remote-host user contract](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/docs/user/devices.md#L89-L108), [remote installer and probe](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/sshDeviceScript.ts#L34-L167).

SSH forwards both hub and agent daemon to server loopback. Device identity includes `hostId`, so identical IDs on different hosts stay distinct. Reconnection refreshes forwarded endpoints; stable config filenames preserve command targeting. Local aliases resolving to the server's own machine are skipped. [SSH port forwarding](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/SshDeviceHost.ts#L213-L333), [multi-host independence test](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/device/DeviceMultiHost.test.ts#L12-L113).

T3 explicitly leaves **app build orchestration, copying/installing build artifacts and Metro/dev-server reachability** to the project/user/agent. A simulator on another machine cannot use the cloud server's localhost without forwarding or a reachable address. To meet Zuse's requested smooth end-to-end iOS workflow, these gaps require deliberate integration rather than assuming the viewer package solves them. [Explicit scope limit](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/docs/user/devices.md#L105-L108), [agent quick-start warning](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/apps/server/src/mcp/toolkits/device/handlers.ts#L64-L66).

Streaming works through the same environment connection as normal app traffic. WebCodecs requires HTTPS or localhost: iOS has MJPEG fallback, Android has no MJPEG video fallback in T3's viewer. Remote plain HTTP is therefore materially worse. Only the visible device tab streams, and closing a viewer stops watching without shutting down the simulator unless explicitly requested. [Streaming constraints](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/docs/internals/devices.md#L75-L85), [viewer lifecycle](https://github.com/pingdotgg/t3code/blob/d6f3af77192adfb2304769096eeec59d3464aa21/docs/user/devices.md#L16-L40).

Recommended Zuse acceptance criteria, inferred from those behaviors:

1. First-use setup explains two helper packages and checks Xcode/runtime/Node independently; merely opening a sidebar item installs nothing.
2. Manual viewer and agent controls have independent permissions; existing provider capability refresh is predictable.
3. Helper installation survives interruption, retries cleanly, never treats a partial tree as complete, and keeps runtime data separate from versions.
4. The server owns one shared device service; renderer/manual tools/MCP use the same host and session identity.
5. Agents get exact CLI commands with host/session/device flags and first-use XCTest progress; installation failures and runner-build failures are distinct states.
6. Viewer visibility is thread-scoped, only visible viewers stream, and closing the UI is distinct from shutting down a device.
7. Remote Macs use authenticated forwarding with reconnect tests and no vendor shell route exposed to clients.
8. A project workflow covers build, transfer/install, app launch and dev-server forwarding explicitly, including cloud-server-to-Mac scenarios.
9. Package engines and platform runtime requirements are validated at the actual supported minimums, including Node 22.12 for this pinned CLI.
10. A real Mac smoke test proves build → install → snapshot → interaction → screenshot → sidebar viewer and reconnection; Linux-only checks cannot establish iOS parity.
