# E2B warm resume repair — 2026-09-16

The final three staging pause/send cycles preserved **runtime generation 2** and
acknowledged delivery in **8.575, 5.881, and 7.946 seconds** after API message
creation. There was no replacement shell, bootstrap, or credential initialization
between these messages. The only restart was the explicit upgrade before testing.
This establishes preserved-runtime delivery in these samples, not a five-second
SLA or successful model-response latency.

## Final change

- Increase reconnect fallback from 500 ms to **12 seconds**, measured after
  provider wake. Ready runtimes proceed immediately. This ceiling allows a
  preserved mailbox HTTP request's existing ten-second timeout, its one-second
  poll interval, and a readiness repair. The startup observer includes this window.
- When the mailbox rejects a lease because the runtime is not ready, the live
  process republishes repository readiness using its existing credential and
  retries the lease once. Authentication failures do not trigger this repair.
- Successful repair explicitly recycles the gateway connection. It does not wait
  for the old WebSocket to notice a broken transport before reconnecting.
- Readiness cannot override a requested pause/archive/delete, an explicit queued
  restart, or a required mailbox generation fence. Both memory and PostgreSQL
  stores enforce these guards. Expired/superseded credentials remain rejected.

## Measurements

All boundaries are seconds after API message creation. API acknowledgement uses
API timestamps. Runtime boundaries span API/VM clocks and may include clock skew.

| Boundary | Run 1 | Run 2 | Run 3 |
| --- | ---: | ---: | ---: |
| Existing runtime restores readiness | 5.001 | 3.600 | 3.991 |
| Gateway reopens | 6.685 | 4.884 | 6.964 |
| Runtime receives message | 7.536 | 5.699 | 7.742 |
| API records delivery acknowledgement | **8.575** | **5.881** | **7.946** |
| Runtime generation | 2 | 2 | 2 |

Median acknowledgement: **7.946 seconds**. Each cycle waited for the API to report
paused, waited three seconds, then sent the same short prompt. Each turn settled
before the next pause. The selected Codex/model combination returned agent-error
outcomes, so these numbers measure runtime readiness and accepted message delivery,
not successful model execution, first token, or answer completion. Longer pauses,
expired credentials, concurrent load, and production distributions were not tested.

A timeout-only experiment increased grace to five seconds while retaining the
old runtime. E2B woke in 880 ms, the API restarted it 5.029 s later, and delivery
took **17.138 s**. Increasing the deadline alone did not restore warm behavior.

The first active-recovery series, still with five-second grace, recorded
18.516/8.332/6.275 s. The first cycle restarted; the other two preserved generation
5. This prompted the final twelve-second fallback. A separate explicit-restart
test exposed readiness racing the restart request; the final API guard fixes that
race. That contaminated diagnostic was deleted and final testing used a fresh
workspace. These small exploratory series are not a controlled performance
distribution; do not report a percentage improvement or hide intermediate failures.
